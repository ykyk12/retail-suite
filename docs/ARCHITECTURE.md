# 架构与设计取舍

## 1. 分层与依赖方向

```
controller（HTTP、权限声明、参数校验）
    ↓
service（业务规则、事务边界、幂等与并发控制）
    ↓
mapper（MyBatis-Plus + 注解 SQL；所有库存相关的"条件更新"写在这一层）
    ↓
MySQL / H2
```

横切关注点：`security`（JWT 过滤器 + 权限拦截器 + 用户上下文）、`audit`（审计）、`common`（统一响应与异常）。

两条人为约束：

1. **库存只能由 `InventoryService` 变更**。商品编辑 DTO 里干脆没有 `stock` 字段——用类型系统防止"改商品顺手改了库存"。
2. **门店隔离靠 `UserContext.storeId()`**，而不是让前端传 `storeId`。跨店访问在服务层表现为"资源不存在"，不泄漏资源是否存在。

## 2. 领域模型

```
store ─┬─ sys_user ── sys_user_role ── sys_role ── sys_role_permission
       ├─ product_category ─┐
       ├─ product ◄─────────┘        （库存就在 product.stock）
       │     ▲
       │     └── inventory_flow      （每一次库存变动一条账，ref_no 指回来源单据）
       ├─ purchase_order ── purchase_order_item
       ├─ sale_order ── sale_order_item（refunded_quantity、cost_price 冻结）
       ├─ daily_sales_summary        （(store_id, summary_date) 唯一）
       ├─ audit_log                  （append-only）
       └─ ai_draft                   （解析中间态，人工确认后才生成单据）
```

设计取舍：
- **金额一律 `DECIMAL(12,2)` + `BigDecimal`**，不用 `double`（浮点误差在收银场景是灾难）
- **明细冗余商品名与条码**：商品改名/改条码后，历史单据与小票不能跟着变
- **库存放在商品表**：单店一商品一库存，拆表只会多一次 join；真正的多仓场景才需要独立库存表

## 3. 并发与一致性（四个场景）

| 场景 | 手段 | 为什么不用别的 |
|---|---|---|
| 收银扣库存 | `UPDATE ... SET stock = stock - n WHERE stock >= n`（条件更新，看影响行数） | 悲观锁会让同商品并发排队、占满连接池；乐观锁要重试；分布式锁在单库场景是多余的失败点 |
| 收银幂等 | `sale_order.request_id` 唯一索引 + 冲突后事务外回查 | 内存 Map 跨实例无效、重启丢；"先查再插"在并发下有竞态窗口 |
| 退货防超退 | `refunded_quantity` 条件更新（`quantity - refunded_quantity >= n`） | 先查再改在并发下会退超 |
| 采购确认入库 | 状态机条件更新（`WHERE status='DRAFT'`） | 避免并发重复确认把库存加两次 |

事务边界原则：**扣库存 + 写流水 + 落单据必须在同一个本地事务**，任一失败整体回滚，因此不会出现"扣了库存没订单"或"有订单没扣库存"。
幂等入口用 `TransactionTemplate` 而不是方法级 `@Transactional`，原因是需要"捕获唯一键冲突后在事务外回查"（见 README 6.2）。

## 4. 报表口径

- **实时**：按 `[from, to)` 直接聚合明细，永远最新（看板）
- **物化**：`daily_sales_summary` 按门店 + 日期预聚合，定时任务默认 00:10 重算昨天与今天；接口幂等（先查后插/改 + 唯一索引）
- **毛利**：成本价在下单时冻结，`毛利 =（销售额 − 已售成本）−（退款额 − 已退成本）`
- **方言中立**：所有聚合用时间区间过滤、按天由 Java 传参，不依赖 `DATE()` / `DATE_FORMAT()`，这样 H2（本地与 CI）与 MySQL（生产）跑同一套 SQL
- **对账**：销售数量与库存出库数量两条独立聚合，在 Java 里比对——比写一条复杂 FULL JOIN 更好读，出问题也更容易定位是哪一侧

## 5. AI 模块

```
用户原话 ──►（配了模型）LLM 解析 JSON ──┐
           └─（未配/失败）本地规则解析 ──┴─► 匹配商品（条码优先，其次名称）
                                              │
                           未匹配的行标注出来，让人工改（不猜）
                                              ▼
                                   ai_draft（PENDING）
                                              │ 人工确认
                                              ▼
                                   采购单（草稿）→ 采购页确认入库才动库存
```

助手侧：模型只做"选工具 + 传参数"，工具全是只读查询（营业额/畅销/库存预警/单品库存/对账），数字由 Java 查库返回。
没配模型时用规则意图识别，功能不降级为不可用。

写操作路径上的三道闸：**草稿不是单据** → **确认只生成草稿态采购单** → **入库仍需采购页确认**。

## 6. 明确的取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 单体 vs 微服务 | 单体分层 | 库存/订单/流水要同库事务；拆开就是分布式事务与补偿，收益为负 |
| 双 DDL（H2 + MySQL） | 保留两份 | H2 用于本地零依赖与 CI（快、无外部依赖），MySQL 用于生产；两者逻辑一致，仅方言差异 |
| JWT 无状态 | 权限码写进令牌 | 省掉每请求查库；代价是改权限需重新登录（要即时失效就上令牌版本号或黑名单） |
| Redis | 已引入但业务未强依赖 | 预留缓存与限流；当前所有功能不依赖它即可跑通，减少演示与部署的失败点 |
| 前端权限 | 只做菜单/按钮显隐 | 真正的鉴权始终在后端；前端隐藏不是安全边界 |

## 7. 演进路径（做到什么规模该改什么）

1. **多店/连锁**：加总部视角的汇总与跨店调拨（数据模型已按门店隔离，改动集中在报表与权限）
2. **超卖敏感场景**：库存扣减前置到 Redis（预扣 + 异步落库），并引入对账补偿
3. **报表数据量上来**：汇总表增量更新（只重算变动天）+ 冷热分离
4. **多实例部署**：会话与幂等切到 Redis/DB，接口限流下沉到网关
